## 12. PANEL QUESTIONS — KNOW THESE ANSWERS
## ─────────────────────────────────────────

Q: Why does the kiosk require a blink before recognizing?
A: Liveness detection via Eye Aspect Ratio (EAR). Prevents photo spoofing.
   The EAR drops below 0.22 for ≥2 consecutive frames = blink confirmed.
   Code location: services/face_service.py → Step 7 LIVENESS HOOK.

Q: What is the TOLERANCE value and why 0.45?
A: Euclidean distance threshold. 0.45 is stricter than dlib's default 0.6.
   Lower = stricter = fewer false positives but more false negatives.
   Configurable via TOLERANCE env var without code changes.

Q: How does debouncing work?
A: After time_in is recorded, subsequent recognitions within 30 seconds
   only update time_out (not create new rows). Enforced by last_seen_dict
   in memory + UNIQUE KEY (user_id, date) at DB level as double guarantee.

Q: How is RA 10173 compliance handled?
A: consent_given=1 must be set before any face_encodings row is created.
   Validated server-side in POST /api/enroll regardless of front-end state.

Q: Where is the liveness hook in the code?
A: services/face_service.py, Step 7 in recognize_frame().
   Comment: "LIVENESS HOOK: Eye Aspect Ratio blink detection implemented here."

Q: Why dlib over DeepFace/TensorFlow?
A: TensorFlow requires ~400MB RAM. Render free tier only has 512MB.
   dlib-bin is pre-compiled (~150MB total), no build required, runs locally.
   For cloud: face recognition is disabled gracefully with a fallback message.

Q: What happens if the database is unreachable at startup?
A: App starts with empty encoding cache. Recognition returns all faces as
   Unknown until DB reconnects and cache is reloaded. Non-fatal by design.

Q: How are face encodings stored?
A: 128-dimensional float64 numpy array serialized with .tobytes() = 1024 bytes
   stored as BYTEA in PostgreSQL. Round-trip: np.frombuffer(blob, dtype=np.float64).
