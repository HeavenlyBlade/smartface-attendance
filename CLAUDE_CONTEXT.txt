## 1. PROJECT OVERVIEW

SmartFace is a real-time face recognition attendance monitoring system built
for St. Anne College Lucena, Inc. (SACLI) as a thesis/capstone project.

Purpose:
  Replace manual attendance roll calls with an automated kiosk that
  identifies registered users via webcam, records time-in/time-out,
  and provides reporting tools for administrators and faculty.

Scope:
  - Local deployment (laptop) for live demo / thesis defense
  - Cloud deployment (Render) for portfolio / remote access (web pages only)
  - Single institution, single campus use case
  - Not designed for multi-tenant or large-scale deployment

## 3. SYSTEM ARCHITECTURE

Browser (getUserMedia, every 500ms)
  → POST /api/recognize  {image: base64 JPEG}
  → face_service.py      (CNN detect → dlib 128-dim encoding → EAR liveness → Euclidean match)
  → attendance_service.py (30s debounce → PostgreSQL INSERT ON CONFLICT)
  → Supabase PostgreSQL

Key design decisions:
  - Server-side recognition: browser only captures and sends frames
  - In-memory encoding cache: loaded at startup, updated after enrollment
  - Thread-safe cache with _cache_lock (threading.Lock)
  - Debounce prevents duplicate rows: 30s minimum between time_out updates
  - UNIQUE KEY (user_id, date) enforces one row per user per day at DB level
  - Session-based lockout: progressive (30s → +10s per failed attempt from attempt 3)
  - 8-hour session timeout

  ip_address VARCHAR, timestamp

## 6. FACE RECOGNITION PIPELINE

Enrollment (POST /api/enroll):
  1. Validate consent_given=1 (RA 10173 compliance)
  2. Decode base64 JPEG samples (3-5 required)
  3. Quality check: Laplacian blur score >= 50
  4. Quality check: face occupies >= 8% of frame
  5. CNN face detection + dlib encoding (num_jitters=5 for robust embeddings)
  6. Check duplicate email/id_number
  7. Transaction: INSERT users + INSERT face_encodings BLOBs + save JPEGs
  8. Write audit log + reload_known_faces()

Recognition (POST /api/recognize, every 500ms):
  1. Decode base64 JPEG
  2. Downscale 0.5x for speed
  3. BGR → RGB conversion
  4. CNN face detection (face_recognition, model="cnn")
  5. dlib 128-dim encoding (num_jitters=3)
  6. Euclidean distance against in-memory cache
  7. TOLERANCE = 0.45 (stricter than dlib default 0.6)
  8. LIVENESS HOOK: EAR blink detection (EAR < 0.22 for >= 2 frames = blink)
     - Requires one confirmed blink before first match acceptance per session
     - Uses dlib 68-point shape predictor (shape_predictor_68_face_landmarks.dat, ~95MB)
  9. Scale bounding box back to original dimensions (x2)
  10. Trigger attendance logging if liveness confirmed

Face encoding storage:
  - numpy ndarray shape (128,) dtype float64
  - Serialized: enc.tobytes() = 1024 bytes
  - Stored as BYTEA in PostgreSQL
  - Deserialized: np.frombuffer(blob, dtype=np.float64)


## 7. KEY FEATURES

Authentication:
  - Progressive lockout: attempt 3 = 30s, +10s each additional attempt
  - Session-based (cookie), 8-hour timeout
  - Generic error messages (no field-level disclosure)
  - Logout confirmation modal

User Management:
  - Search bar (PostgreSQL ILIKE, case-insensitive)
  - Encoding count badge per user (enrolled/not enrolled)
  - Edit profile, Deactivate/Reactivate, Re-enroll, Delete (all with confirmation modals)

Dashboard:
  - 4 summary cards: Present, Late, Absent, Registered Users
  - 7-day bar chart (Chart.js)
  - Today's donut chart
  - Live-updating attendance table (every 3s, /api/live-feed)
  - Confidence color coding: green ≥90%, gold 70-89%, red <70%

Kiosk:
  - Full-screen, viewport-locked (no scroll)
  - MediaPipe FaceMesh overlay (face mesh, scan line animation, corner brackets)
  - 500ms capture interval
  - Brightness warning (brightness < 50/255)
  - Audio cues: ascending chime on match, low tone on Unknown
  - Face mesh drawn via requestAnimationFrame (60fps, smooth)

Reports:
  - Filter by date range, role, department
  - CSV export (9 columns)
  - PDF export (A4 landscape, ReportLab, SACLI-branded)
  - Client + server-side date validation

Audit Log:
  - Reverse-chronological, paginated
  - Filter by action type and date range
  - Clear button (JS-driven, bypasses browser cache)

Data Privacy:
  - RA 10173 (Data Privacy Act of Philippines) compliance
  - consent_given=1 required before any face encoding stored
  - Validated server-side regardless of front-end state

Liveness / Anti-spoofing:
  - EAR (Eye Aspect Ratio) blink detection
  - Requires one blink before match acceptance
  - Prevents photo and screen spoofing
  - Comment in code: "LIVENESS HOOK" at exact insertion point


## 8. LIMITATIONS (known, documented)

1. Face recognition disabled on Render free tier
   - Reason: dlib compilation fails (OOM, 512MB RAM limit)
   - Impact: Kiosk shows "Waiting for face..." on cloud
   - Mitigation: Run locally for demo; Render is portfolio only

2. Uploaded face JPEG files are ephemeral on Render
   - Reason: Render free tier has no persistent filesystem
   - Impact: Raw enrollment images wiped on each redeploy
   - Mitigation: Face encodings stored in Supabase (survive redeploys)

3. No GPU support
   - dlib-bin is CPU-only (no CUDA build)
   - CNN detection is slower than GPU (~200-400ms per frame)
   - Acceptable for single-kiosk demo use

4. Supabase free tier pauses after 7 days inactivity
   - Mitigation: Windows Task Scheduler runs keepalive.py daily at 9AM

5. Render free tier sleeps after 15 minutes idle
   - Mitigation: UptimeRobot can ping /login every 5 minutes (optional)
   - For demo: open site 2 minutes before panel arrives

6. No password reset UI
   - Enrolled users keep "Admin123" until manually updated via DB

7. No email notifications
   - No SMTP integration

8. Single webcam only
   - System assumes one webcam per machine

9. Liveness requires blink before EVERY new session
   - If server restarts between sessions, users must blink again
   - _liveness state dict is in-memory, not persisted

## 12. WHAT A REVIEWER SHOULD EVALUATE

Technical quality:
  - Is the architecture appropriate for a thesis-level project?
  - Are the design decisions (dlib vs DeepFace, local vs cloud) well-reasoned?
  - Is the code organized and maintainable?
  - Are security concerns (RBAC, lockout, RA 10173) handled adequately?
  - Is the property-based testing approach valid and meaningful?

Academic / thesis criteria:
  - Does liveness detection (EAR blink) qualify as a meaningful contribution?
  - Is the LIVENESS HOOK comment sufficient for panel discussion?
  - Are the correctness properties (12 total) adequate for the system?
  - Is the system's scope appropriate for a capstone project?

Deployment strategy:
  - Is the local-primary / cloud-secondary approach defensible?
  - Are the known limitations documented and justified adequately?

Potential weaknesses to flag:
  - EAR liveness is basic (can be defeated with a video of someone blinking)
  - No GPU = CNN detection is slow (~300ms per frame)
  - Supabase free tier limitations could be a concern for panelists
  - No unit test coverage for the new features (liveness, PDF, charts)
  - The face_recognition library uses a 2015-era model; modern alternatives exist

Potential strengths to highlight:
  - Full-stack implementation: DB, backend, frontend, AI pipeline
  - Live face mesh overlay gives professional visual feedback
  - Property-based testing demonstrates rigorous correctness verification
  - RA 10173 compliance is a real Philippine legal requirement
  - Graceful degradation (cloud works without face recognition)
  - Comprehensive audit trail (audit_logs table, all actions recorded)
